# 日报运行与维护

## 三层分工

| 层级 | 运行位置 | 作用 |
|---|---|---|
| 新闻更新 | GitHub Actions，每小时第 17 分钟 | 采集 12 个公开来源、筛选、生成 RSS 并发布 Pages |
| 发布验收 | 同一工作流的 verify job | 检查线上首页、RSS、数据时间与本次发布一致性；旧缓存不能冒充新部署 |
| 独立巡检 | 维护者自己的 Codex 定时任务 | 每天北京时间 09:30、21:30 检查线上状态；健康时安静，异常或恢复时才报告 |

Codex 巡检配置保存在维护者本机，不在本仓库中，也不会随 fork 自动复制。
它是额外保障，执行取决于该 Codex 任务和设备是否可用；网站的每小时更新仍由 GitHub 托管运行。巡检间隔不等于实时报警。

## 什么算异常

- 首页、公开 JSON 或 RSS 无法读取，或内容格式无效。
- 数据超过 4 小时未更新，时间明显来自未来，或 JSON 版本相互不一致。
- 发布验收看到的线上数据早于本次构建的快照时间。
- 公开模式不正确，或邮件、付费通道没有明确关闭。
- 少于 6 个信源正常，或新闻被错误放进 24 小时窗口。

单个信源失败标记为 degraded，不阻止其他有效新闻发布；巡检会区分单源降级和整站故障。0 条新闻不自动等于故障。

## 手动检查

无需 API Key，也无需安装第三方 Python 依赖：

```sh
python scripts/check_health.py --attempts 2
```

输出仅包含状态、采集时间、条数、失败信源名称和问题代码，不输出抓取正文或凭据。
healthy / degraded 返回 0；unhealthy 返回 1。

查看运行或手动补跑（需要自己的 GitHub 登录）：

```sh
gh run list --repo homerzhou6778-tech/ai-daily --limit 5
gh workflow run update-pages.yml --repo homerzhou6778-tech/ai-daily --ref main
```

## 恢复规则

先检查正在运行的任务，避免重复触发。若工作流因长期无仓库活动而自动停用，可重新启用；若是维护者手动停用，则保持暂停。
数据过期且没有正在执行的更新时，可补跑一次，再等待结果并验证线上数据。
同一故障不反复重跑，持续失败应查看日志和具体信源原因。
不通过提交无意义文件来维持仓库活跃，不自动添加付费 API、邮箱或 cookies。

GitHub 对工作流失败的通知由账号自身通知设置控制。额外巡检在出现新问题、故障恢复或需要人工操作时才向维护者报告。

网站的“使用与信源说明”入口位于页脚：`about.html`。它解释来源、筛选和数据时效，不要求读者理解部署或配置细节。
